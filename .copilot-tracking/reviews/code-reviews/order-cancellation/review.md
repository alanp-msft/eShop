## Decisions for approvers

The following decisions were made by the implementing/orchestrating agents while executing the plan and are carried forward for explicit approver sign-off rather than re-litigated here:

* **A1 (REQ-004 reading)** — `Catalog.API` never reserves stock before `Paid`, so cancellation (only reachable from `Submitted`/`AwaitingValidation`) never needs to release a reservation; the new Catalog subscriber logs receipt and deliberately never touches `AvailableStock`. **Recommendation: accept.** REQ-004's literal "reserved quantities return to available stock" wording is satisfied vacuously under the current stock model, and the plan's own P06 validation (finding 7) already flagged this as needing `{{tech-lead}}` sign-off; the test (`Catalog.UnitTests`) correctly proves the no-op, not a false "reservation released" claim.
* **A4 (409 for `IneligibleStatus`)** — `CancelOrderResult.IneligibleStatus` (StockConfirmed/Paid/Shipped) maps to `409 Conflict`, not `400`. **Recommendation: accept.** `409` is the more semantically correct RFC 9110 status for "the request conflicts with the current state of the resource" and satisfies REQ-001's "surfaces this as a client error rather than a 500" without over-specifying which 4xx code.
* **A5 (audit approach)** — REQ-008 is satisfied by a structured `ILogger` entry (`OrderingApiTrace.LogOrderCancelledByCustomer`, `EventId=4`) rather than a persisted order-history table row. **Recommendation: accept**, conditional on `{{tech-lead}}` confirming the log sink's retention/access controls meet the `confidential` classification's audit-query needs (SEC-TEMP-7/-8 in the security plan already track this as a separate, lower-priority backlog item); the log entry itself is structured and queryable by `OrderId`/identity as REQ-008 requires.
* **P05 (succeeded-before-commit)** — `order_cancellations_succeeded` increments inside the handler before `TransactionBehavior` commits the surrounding transaction and dispatches the outbox, so a post-handler commit failure is neither subtracted nor counted as `failed`, and a retrying execution strategy could double-count. **Recommendation: accept as a documented limitation** (already disclosed in the change record and P05 validation) for this PR; track the suggested pipeline-behavior follow-up as a separate backlog item rather than blocking this merge, since publish health remains independently observable via the existing outbox/event-bus telemetry.
* **P07 (banner persistence)** — the success banner on `/user/orders` can be dropped early if `OrdersRefreshOnStatusChange`'s `Nav.Refresh()` fires (via the integration event) before the user reads it; no redirect-with-query-string persistence was implemented. **Recommendation: `{{ux-owner}}` decides.** REQ-006's acceptance criteria are met either way (status converges to `Cancelled` without a manual reload), so this is a UX-polish call, not a correctness gap.
* **P08 (CI execution)** — the four new/retargeted `Ordering.FunctionalTests` Facts were compiled but never executed in this session (no Docker on the implementing host). **Recommendation: do not accept as-is** — this is elevated to a merge condition in the Verdict above rather than a soft carry-forward, because it is the only evidence for REQ-002/REQ-005/REQ-007 at the HTTP-pipeline level and the P08 validator gave a specific, concrete reason (anomalous CI timing plus a defect that would have failed the suite) to distrust an unexamined green CI run.
