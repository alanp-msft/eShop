## Gaps

* **REQ-002** — the acceptance criterion's `401 Unauthorized` clause (unauthenticated caller) is not covered by any executed or compiled test in this change. It is enforced only by `.RequireAuthorization()` on the route group; `Ordering.FunctionalTests`' `AutoAuthorizeMiddleware` authenticates every request in-process, so the fixture cannot exercise the unauthenticated path even once Docker is available. Confirmed in `.copilot-tracking/reviews/rpi/2026-09-17/order-cancellation-p08-validation.md` (finding 4, "Note") and `.copilot-tracking/reviews/rpi/2026-09-16/order-cancellation-p03-validation.md`. No test defect to fix; this is a known, accepted coverage boundary of the test host, carried to the `pr` gate.
* **REQ-005** — "downstream subscribers receive and process exactly one event" is asserted at the `IntegrationEventLogEntry` (outbox) row written inside the same transaction as the cancellation, not at actual message-bus delivery to a subscriber. Confirmed in `.copilot-tracking/reviews/rpi/2026-09-17/order-cancellation-p08-validation.md` (finding 5, "Note": "asserted at the outbox row, as the plan scoped it, not at bus delivery"). RabbitMQ is not present in the functional-test fixture; a failed publish is caught and marked `PublishedFailed` without affecting the HTTP result, so the outbox-row assertion is the strongest signal obtainable without a real broker.
* **REQ-004** — the Catalog-side stock-release behavior is verified under Assumption A1 (no reservation exists prior to `Paid`), per the ADR (`docs/decisions/2026-09-15-order-cancellation-authorization-and-events.md`) and `.copilot-tracking/reviews/rpi/2026-09-16/order-cancellation-p06-validation.md`. The single `Catalog.UnitTests` test (`OrderStatusChangedToCancelledIntegrationEventHandlerTest`) exercises the handler under that assumption; it does not prove correct behavior for a hypothetical pre-`Paid` reservation model, since the codebase does not reserve stock before `Paid` today.
* **REQ-009** — `order_cancellations_succeeded` (and the `rejected`/`failed` counters) increment synchronously inside `CancelOrderCommandHandler.Handle`, before `TransactionBehavior` commits the surrounding transaction and dispatches the outbox. A commit failure after the handler returns success is not reflected as `failed`, and a retrying execution strategy could double-count. This is documented as an accepted, known limitation in `.copilot-tracking/reviews/rpi/2026-09-16/order-cancellation-p05-validation.md` (finding 3): "`succeeded` means 'handler reached success', not 'committed and published'". No test in this session exercises the commit-failure-after-count scenario; it is not covered.
